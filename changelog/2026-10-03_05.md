## Why Care?

What happens when someone takes your product and rebuilds it their own
way? A while ago Michael asked for a version of dididecks-ai that people
could log into and use. phoenixcap took that and built **Instadeck**: a
SvelteKit front end, a FastAPI back end with workers and a separate
renderer, Postgres, and Railway deploys. Same goal, very different
machinery.

That makes a rare kind of comparison: one product, two approaches, both
built with coding agents. We ran our [[2026-10-03_02|three-step
collaboration relay]] on it, using the [[2026-10-03_03|two-harness lens]]
from this morning. We framed it as differences between approaches, not a
contest.

## How it Works

### Each side put its depth where its generator lives

|  | Developer-agents harness | In-product-agents harness |
|---|---|---|
| **dididecks-ai** | Deep in context | Moderate |
| **Instadeck** | Moderate | Deep |

dididecks-ai generates decks *inside an operator's Claude Code session*,
so its developer harness (instructions, data-model docs, plans, shared
skills) does double duty as its product harness. Instadeck generates decks
in a *server pipeline a customer starts*, so the product machinery lives
in the backend, deliberately walled off from development memory.

### The most interesting difference: she turned our memory into product

Instadeck adopted our `context-v/` and `changelog/` conventions, then a
week later replaced them with per-customer database records, plus a test
that fails if the folders come back. Both choices are coherent. Ours
makes memory cheap to grow and easy for an agent to read. Hers makes it
typed and safe to expose to strangers.

### Where they converged

Both write a deck as Markdown before rendering it, with a per-deck
`DESIGN.md`, and both reason about the whole deck before any single slide.
She tried a simpler path and reverted it because it bypassed that
authoring model.

### What each could borrow

- **From Instadeck:** tests that pin specs and prompts so they can't
  drift, a written definition of what a good deck is, and a frozen render
  corpus. dididecks-ai has no tests today.
- **From dididecks-ai:** an instruction file on `main`, and the deep
  context (data-model docs, sitemap, plans) that gives a fresh agent its
  bearings.

## Under the Hood
